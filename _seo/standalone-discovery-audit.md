# 単発実況 候補抽出精度監査の記録

公開サイトには出ない(Jekyll は `_` で始まるフォルダを出力しない)。`discover-standalone.ps1` を本番運用に使えるかを判断するための記録。

## 第1回(2026-09-30、単発実況PoC #1 の直後)

### 結論

- 判定: **B**(候補抽出には使えるが、本番投入前の人間確認が必須。判定ロジックの改善が先)
- HIGH(監査ルール)Precision: 9/9 = 100%。ただし n=9 と少なく、HIGH 判定はスクリプトに未実装(監査側で付けた分類)
- スクリプト出力そのものの Precision: 25/28 = 89%(誤判定3件はすべて説明欄の部分一致)
- 簡易Recall: 25/38 = 66%(取りこぼしの大半は GAMES 未登録)
- playlist 重複排除: 4/4 成功、失敗0
- 推奨運用: 半自動(HIGH 候補を生成 → 人間確認 → 承認分だけ登録)
- 本番データ・コードの変更なし。STANDALONE_PLAYS は1件(宙科そぴあ × 夜勤事件)のまま

### 方法

- 会社PC(YouTube APIキーなし・Node.jsなし)で実施。公開ページ(チャンネルの配信/動画/再生リストタブ、各動画のwatchページ、登録済み再生リストのページ)を取得し、YouTube API と同じ形の模擬レスポンスを作成
- 修正済み `discover-standalone.ps1` を作業用コピーで実行し、`ApiGet` だけを模擬に差し替え(判定ロジックは本番と同一)。説明欄も watch ページから取得して照合対象に含めた
- 取得: 公開ページ 194リクエスト(APIクォータ消費なし)
- 限界: 登録済み再生リストのうち4件は非公開・削除動画のため公開ページで一部しか取れなかった(轟はじめ「バイオハザード ヴィレッジ」0/6・「バイオハザードシリーズ」0/5・「ARK」7/8、儒烏風亭らでん「Hookah Haze」3/4)。いずれも古いゲームで、今回のサンプル(直近)とは重ならない

### 監査用の信頼度ルール(スクリプトには未実装)

- HIGH: タイトルの【】/[] の中身が、一致したゲームの name / alias と完全一致

### 重複排除

- playlist重複: 登録PLに入っている動画のうち、排除しなければ候補になっていた4本(Coffee Talk Tokyo #5、ほの暮しの庭 #07/#08、DARK SOULS III #9)は、すべて候補から除外された。成功4 / 失敗0
- STANDALONE_PLAYS重複: 宙科そぴあ × 夜勤事件は discover では**除外されず再提案される**。登録しようとすると validate-data.ps1 の「単発:video ID重複」で止まる(二段目で防げているが、一段目で落とすべき)
- VTuber×game重複: 正解25本のうち14本(Minecraft・7 Days to Die・首都高バトル)は、同じVTuber×ゲームの再生リストが登録済みで、validation で止まる。discover はこれを warning として出すだけで候補から外さない

### 誤判定のリスク(重点)

1. **説明欄の部分一致**: UNO の3件。短い英字名(3〜4文字)は単語境界なしだと URL や ID の中でも一致する
2. **最長一致が説明欄を優先する**: 「【DARK SOULS III】#9」が説明欄の「DARK SOULS REMASTERED 完結 再生リスト」に一致し、別ゲームと判定された(今回は登録PL内のため排除されたが、PL外なら誤登録になる)
3. **似た名前のゲーム**: 「Coffee Talk Tokyo」が「Coffee Talk」と判定された(同じ理由で、今回は排除された)
4. 短いゲーム名: PEAK はタイトル内の一般語と重なる(今回はゲーム自体は正解)
5. タイトルに複数のゲーム名がある / 「○○風ゲーム」: 今回のサンプルには無し

### APIクォータ

- 今回の呼び出し(模擬): channels 8 + channels(forHandle)2 + playlists 8 + playlistItems(登録PL)75 + playlistItems(アップロード)8 = 101回。実際のAPIでは、50件を超える登録PLと MaxVideos=200 のアップロード取得が複数ページになるため、約130ユニット
- 全VTuber(293人・登録PL 6,562件)を毎回全件取得した場合: 登録PLの読み込みだけで約7,000ユニット、合計で約9,500ユニット。1日の既定クォータ(10,000)をほぼ使い切るため、全件の再取得は不可
- 差分取得を前提にした見込み:
  - アップロードは先頭1ページだけ取得し、前回の最新 video ID まで読む(約300ユニット/日)
  - 登録PLの動画IDはキャッシュする。itemCount が変わったPLだけ再取得する(`refresh-playlist-meta.ps1` の itemCount 差分キャッシュを流用)
  - channels.list は50件ずつまとめて取得する
  - 合計で1日あたり数百ユニット程度

### 推奨運用

- **半自動(B)**: HIGH 候補を生成 → 人間が確認 → 承認分だけ STANDALONE_PLAYS に追加 → validate-data.ps1
- 完全自動は不可。理由は3点:
  - HIGH ルールがスクリプトに未実装
  - 説明欄の誤一致や最長一致の誤りが実際に起きている
  - 登録可能かどうか(VTuber×game の再生リスト優先)を discover 側で判定していない
- 手動のみは効率が悪い。候補の出る場所としては十分役に立つ(正解25本)

### 判定ロジックの改善案(次工程)

1. 信頼度(HIGH/MEDIUM/LOW)をスクリプトに実装する。【】の中身と name/alias の完全一致だけを HIGH にする
2. ゲーム判定はタイトルを優先する。説明欄は「配信タイトル:○○」の行だけ参考にし、それ以外の説明欄一致は LOW に落とす
3. 英数字のゲーム名は単語境界つきで照合する(UNO の誤一致を防ぐ)
4. 候補の段階で除外する:
   - STANDALONE_PLAYS に登録済みの video ID
   - 同じVTuber×ゲームの再生リストが登録済みのもの
   - #1 / #2 などの連番付き
   - チャンネル側に専用PLがあるもの(再生リスト方式へ回す)
5. 差分取得: アップロードの既知 video ID と、登録PLの video ID キャッシュ
